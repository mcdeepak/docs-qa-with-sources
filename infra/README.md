# Azure infrastructure

Terraform for running this system on Azure. It has been checked with
`terraform fmt` and `terraform validate`. It has not been deployed.

```bash
cd infra
terraform init -backend=false
terraform validate
```

## What it defines

| Resource | Purpose |
|---|---|
| Container Apps environment, two container apps | The API (public HTTPS) and the worker (no ingress). Same image, different command, as in `docker-compose.yml`. |
| PostgreSQL Flexible Server | Documents, passages and the job queue. |
| Container Registry | Holds the application image. |
| Key Vault | Database URL, login password and session key. |
| User-assigned managed identity | Lets the containers pull the image and read secrets without stored credentials. |
| Log Analytics workspace | Container logs. |
| Azure OpenAI account and model deployment | Only when `enable_ai = true`. Off by default. |

## Why these choices

**Container Apps rather than AKS or App Service.** The system is two small containers.
Container Apps runs them with HTTPS, scaling and revisions without a cluster to
operate. App Service would handle the API but is a poor fit for a worker with no HTTP
endpoint. AKS is more than a small team should maintain for this.

**The same shape as local.** The API and worker run the same image with the same
environment variables as in Docker Compose. What was tested locally is what runs.

**Postgres for the queue, not Service Bus.** The queue is a table claimed with
`FOR UPDATE SKIP LOCKED`. Saving the upload and queuing its job commit together, so
there is no window where one exists without the other. At tens of documents a separate
broker would add a service and a failure mode for no gain. If volume grew to many
uploads per second, the claim function in `worker.py` is the one place to swap in
Service Bus.

**Files in Postgres, not Blob Storage.** Policy documents are small, and keeping the
bytes beside the job row is what makes an upload atomic. Blob Storage becomes the right
home when files are large or need lifecycle rules; the note in the repository root
lists this as a next step.

**No Azure AI Search.** The brief requires the system to work with no model, and
keyword search over a few hundred passages takes about a millisecond in process. AI
Search has a fixed monthly cost and would add little here. It is the natural upgrade
for hybrid or vector search across thousands of documents, and would slot in as a new
`Retriever`.

**Secrets in Key Vault, read through a managed identity.** No password appears in the
container configuration or in Terraform outputs. Passwords are generated by Terraform.
They do end up in Terraform state, so state must be kept in a locked-down backend.

**Burstable database tier and scale limits.** `B_Standard_B1ms` and one to three API
replicas suit a small internal tool and keep the monthly cost low. Both are single
lines to change.

**Australia East by default.** Keeps the data onshore for an Australian team.

**Tags on everything.** `product`, `environment` and `cost-centre` so spend can be
attributed in Cost Management.

**The model is optional.** `enable_ai = true` adds an Azure OpenAI deployment, stores
its key in Key Vault and sets `ANSWERER=llm`. The application's quote check applies
either way.

## What production would add

- Private networking: VNet-integrated Container Apps and a private endpoint for
  Postgres, replacing the "allow Azure services" firewall rule.
- Microsoft Entra ID sign-in in place of the shared login.
- Remote Terraform state in a storage account with locking.
- Zone-redundant Postgres and a general-purpose tier if the tool becomes critical.
- Alerts on failed jobs and on the rate of declined questions.
- Managed-identity authentication to Azure OpenAI instead of an API key.
